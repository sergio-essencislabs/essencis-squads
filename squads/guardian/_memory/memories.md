## Técnico (específico do squad)

- **Sob contenção pesada de I/O/rede (muitos agentes paralelos), `gh pr merge`/`gh pr view --json` (GraphQL) falham com `TLS handshake timeout` mesmo quando a operação já teve sucesso no servidor** — confirmado 2x (PRs #360 e #361 apareceram como falha/timeout no client, mas já estavam `merged=true` no GitHub ao checar depois). **Usar `gh api -X PUT repos/{owner}/{repo}/pulls/{n}/merge -f merge_method=squash` (REST) e `gh api repos/{owner}/{repo}/pulls/{n} --jq '.state,.merged'` para checar** — mais leve que GraphQL, e sempre conferir o estado real antes de reenviar um merge que "falhou" no client (nunca assumir que falhou de verdade sem checar).

- **Dispatch paralelo em massa (11 agentes simultâneos, Onda 3, 2026-09-02) causou contenção real de I/O**: `npm ci`/`ng build`/`ng test` não conseguiram terminar em pelo menos 1 agente (GT-0024) — `node_modules` travado em progresso parcial por vários minutos, até comandos básicos de shell estourando timeout. Validação ficou limitada a revisão estática de código nesse caso. **Lição para próximas ondas**: 11 worktrees simultâneos rodando `npm ci` ao mesmo tempo no mesmo host é demais — considerar lotes menores (5-6) ou espaçar a instalação de dependências, e **sempre rodar uma validação de build/test consolidada no repositório principal depois que uma onda inteira mesclar**, já que PRs individuais podem ter sido mesclados sem essa confirmação por causa da contenção.

- **Dispatch paralelo via Agent tool com `isolation: worktree` — risco real de `.git` compartilhado (achado em 2026-09-02, GT-0007)**: apesar de cada agente rodar em seu próprio worktree (`.claude/worktrees/agent-{id}`), um agente encontrou evidência de outra sessão concorrente mexendo no mesmo `.git` (arquivos de terceiros modificados, um `git stash` seu sobrescrito por stash de outra sessão). Recuperou sem perda (staged só os próprios arquivos por caminho explícito, nunca `git add -A`), mas o risco é real — worktrees isolam a árvore de trabalho, não necessariamente todo o estado de `.git` (stash é compartilhado entre worktrees do mesmo repo). **Ao despachar muitos agentes em paralelo no mesmo repo, nunca usar `git stash` sem depois verificar `git stash list`/conteúdo antes de aplicar de volta, e sempre `git add <arquivos específicos>`, nunca `-A`.**

- **Risco de infraestrutura descoberto ao dar push direto na `main` (2026-09-02)**: o diretório de trabalho principal (`C:\Software\GeoCloud\GeoCloudAI`) é compartilhado por várias sessões/agentes em paralelo, cada um podendo estar em um branch diferente (confirmado: uma sessão trocou o `HEAD` para `refactor/orderable-columns-standardization` com 22 arquivos não commitados enquanto esta run tentava publicar no `main` — não era trabalho meu, quase foi atropelado). Mudanças não commitadas ficam soltas no disco, não "presas" a um branch — um `git checkout` para `main` nesse estado não as descarta, só passa a mostrá-las como diff contra outro branch, o que pode confundir ou, pior, ser incluído por engano num commit (`git add -A`) que não é dele. **Regra a seguir sempre que for dar push direto na `main` a partir deste diretório compartilhado**: (1) nunca `git checkout main` direto aqui se `git status`/`git branch -v` mostrar HEAD em outro branch com mudanças não commitadas de outra sessão; (2) usar um `git worktree add <tmp> main` isolado, rebasear/mesclar lá, buildar, dar push, depois `git worktree remove` — nunca toca no checkout compartilhado; (3) sempre `git fetch origin main` antes de qualquer push, porque outra sessão pode já ter mergeado algo no `origin/main` entre o commit local e o push (aconteceu aqui: PR #306 de outra sessão entrou no meio). Vale para GeoCloud e ELIMS igualmente, já que ambos têm o mesmo padrão de múltiplos branches/worktrees compartilhando pasta.
- **Conflitos reais de merge entre PRs paralelos que tocam o mesmo componente compartilhado, projeto Visualizadores/Navegação/Layout (2026-09-02)**: quando duas tasks independentes adicionam cada uma seu próprio `@Input()`/`@Output()` ao mesmo componente Angular compartilhado (`ViewerToolbarComponent`/`ViewerMenuComponent`, tocado por GT-0008, GT-0009, GT-0010 em paralelo), o segundo PR a ser mesclado sempre gera `mergeable_state: dirty` no GitHub — **`gh api .../pulls/{n}` demora alguns segundos para calcular `mergeable` depois de um push** (`mergeable: null` logo após, virando `true`/`false` real só depois de ~5-10s; sempre reconferir antes de decidir). Quando dá conflito real (confirmado em GT-0009×GT-0010): resolver direto no worktree do agente que ainda está aberto (`git fetch` + `git merge origin/<branch-integração> --no-edit`), união simples dos dois lados (`<<<<<<<`/`=======`/`>>>>>>>`) quando as duas features são aditivas e independentes (nunca escolher um lado e descartar o outro sem ler os dois primeiro) — rodar `ng build`/`dotnet build` no worktree **depois do merge, antes do push**, nunca confiar só no `mergeable: clean` do GitHub como prova de que compila. **Lição de processo**: depois de despachar N agentes em paralelo no mesmo componente compartilhado, esperar conflito de merge sequencial como o caso normal, não a exceção — não é preciso serializar o dispatch, só o merge.
